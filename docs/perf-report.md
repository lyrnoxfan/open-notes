# 性能优化报告

基线见 `docs/perf-baseline.md`。本报告只写「改了什么、前 → 后、为什么」，不重复基线的手法。

**所有运行时数字都来自 x86_64 软件渲染模拟器**（沙箱里没有 arm64 ColorOS 手机）。真机数字需要你在手机上复测，见文末清单。体积数字与设备无关，可以直接当验收依据。

## 2. 体积

### 2.1 只打一个 ABI —— `f4fb21d`

`libsqlcipher.so` 四个 ABI 共 22.5 MB，占了 28.3 MB 包体的 80%。个人安装只会用到 arm64-v8a。

- release：仅 `arm64-v8a`；debug：`arm64-v8a` + `x86_64`（设备测试跑在 x86_64 模拟器）
- `-PabiSet=all` 恢复四 ABI 通用包，供在 x86 模拟器上验收正式包
- README 与 `docs/release.md` 里「含四个 ABI」的描述已同步改写

实测：**28,289,143 → 11,234,043 B（−60.3%）**。

### 2.2 只保留两种语言 —— `fb593ac`

依赖库带进几十种语言的翻译，应用本身只有中文。保留 `zh` 与 `en`（英文作为库字符串的回退）。

实测：**11,234,043 → 10,890,429 B（−3.1%）**，`resources.arsc` 0.44 → 0.11 MB。

用 `resourceConfigurations` 而不是 `localeFilters`：后者要到 AGP 8.9 才有，本项目锁在 8.7.3。

### 2.3 图标库是否被 R8 裁掉 —— 只确认，未改动

`apkanalyzer dex packages --defined-only` 与 `strings classes.dex | grep material/icons` 都是 **0 命中**：
`material-icons-extended` 的未用图标已被 R8 完全裁掉，dex 里没有残留类。因此不需要「只拷贝用到的几个图标」。

### 2.4 R8 之后最大的 6 项

| # | 条目 | 体积 |
| --- | --- | --- |
| 1 | `lib/arm64-v8a/libsqlcipher.so` | 6.27 MB |
| 2 | `classes.dex` | 3.37 MB |
| 3 | `res/35.ttf`（霞鹜文楷子集） | 3.29 MB |
| 4 | `resources.arsc` | 0.11 MB |

再往下降就要动字体（设计验收要求它）或 SQLCipher（底线 3 禁止升级），所以到此为止。

## 3. 速度

### 3.1 摘要提取 —— `21bfb7b`

列表只画两行摘要，`plainExcerpt` 却在**全文**上跑三个正则，每行每次重组都跑一遍。

- 先把围栏代码块剥掉（需要原文），再 `take(300)`，然后才跑标点与空白正则
- 结果用 `remember(note.id, note.updatedAt)` 缓存：每篇一次，不再是每帧一次

实测（同一次运行内对比旧实现，500 KB 样本 ×20 次）：**97.4 → 29.2 ms/次（−70%）**。

输出对 300 字以内的笔记完全不变；列表标记 `-` 本来就不在标点集合里，`PlainExcerptTest` 把这一点也钉住了。

### 3.2 搜索防抖 —— `fbbb454`

搜索是 `LIKE '%term%'`，用不上索引，每个按键一次全表扫描。

- `debounce(250 ms)`；清空搜索框用 0 ms，立即生效
- 拼音输入法一次上屏一串字符，组合过程不会逐字触发

实测（数查询次数，不靠时间）：四键 "会/会议/会议记/会议记录" 从 **5 次降到 2 次**（首次空查询 + 一次稳定后的搜索）。

### 3.3 预览解析离开主线程 —— `95c5fae`

`markwon.setMarkdown` 原来在组合线程上跑，大文档直接卡住用户正在等的那一帧。

- parse + render 移到 `Dispatchers.Default`，结果就绪后再交给 TextView（在此之前保留上一帧文本，不闪空）
- 每个预览一个 `AtomicLong` generation：旧结果晚到不会覆盖新结果，两个预览也不会互相取消

实测（200 KB Markdown，parse+render）：主线程 **46,406 ms → 0**；Default 上 wall 34,346 ms。绝对数字是模拟器软渲染的，看比例。

### 3.4 列表投影查询 —— **测量后回滚**

原本按方案把 `SELECT *` 改成 `substr(content,1,300)` 的投影。交替 A/B 各 5 轮取中位数：

| | 全字段查询 | 投影查询 |
| --- | --- | --- |
| 首次发射中位数 | **448 ms** | **768 ms（慢 1.7×）** |

原因是数据集形态：5,000 条里只有 1 条特别大，`substr` + `length` 要给每行算一次，省下的传输抵不过全表计算。

结论：**回滚**，只保留 3.1 那个与查询无关的 UI 层修复。A/B 工具留在 `PerfBaselineTest` 里，换一种数据形态（比如大笔记占比高）可以重跑。
如果将来的数据以长笔记为主，这个改动的收益方向会反转；现在的数据不支持它。

### 3.5 编辑器输入路径 / 中文输入法 —— `ab4dfa2`（P1 修复）

`docs/test-report.md` 的 P1：编辑器每帧用 `TextFieldValue(text, selection)` 重建值，该构造函数不带 composition，每次状态回写都把拼音组合区扔掉。

- `TextFieldValue` 改由 `EditorContent` 用 `rememberSaveable` 持有，原样交给 `BasicTextField`
- ViewModel 的字符串单向回灌，且只在「没有组合态 + 文本真的不同」时发生
- 光标与组合区现在还能跨配置变更存活
- 自动保存行为不变：1 秒防抖、离屏刷新、ON_STOP 刷新

`EditorCompositionTest` 的断言已从「缺陷存在」翻转为「组合区被保留」；`EditorAutoSaveTest`、`NoteEditorViewModelTest`、设备端 `EditorInputRoundTripTest` 全绿。

### 3.6 Baseline Profile —— 不做（`95c5fae` 之后仍不做）

方案第 10 条的前提是「先看冷启动数字，没有明显收益就不做」。基线的冷启动是模拟器软渲染下的 5013 ms，不能用来判断真机是否需要 Profile；而生成 Profile 本身要跑 Macrobenchmark，在这台机器上不现实。**留给你在真机上测**，见文末。

## 6. 【需决策】四项方案（只写方案，未动代码）

### 6.1 开库跳过 KDF（对应方案第 8 条）

**现状**：每次锁定都关库、解锁重开，SQLCipher 每次打开做 256,000 次 PBKDF2。基线实测 **369 ms**（模拟器；真机预计 80–200 ms）。超过方案给的 300 ms 阈值，所以按约定写在这里。

**方案 A：保持现状。** 改动面 0。代价是每次解锁多等 0.1–0.4 秒，而且这个等待发生在指纹成功之后、首屏出现之前。
**方案 B：改用 raw key。** 用 `PRAGMA key = "x'<64 hex>'"` 直接给 SQLCipher 32 字节密钥，跳过 KDF。
- 改动面：`EncryptedDatabaseProvider`（底线 1 文件）、一次性的 `PRAGMA rekey` 迁移、迁移失败的回滚路径、以及「迁移中断后库还能不能开」的测试。
- 风险：迁移必须在密钥可用时一次完成；中途杀进程可能留下半迁移状态的库。现有「开库后复查文件头」的防护要继续通过。
- 测试计划：迁移前后逐条比对行数与内容 hash；迁移中杀进程后能重开；`KeyUnavailable` 路径不变。
**需要你决定**：是否接受为一个 0.1–0.4 秒的等待去改底线 1 的文件。

### 6.2 自动备份永远是明文（对应方案第 13 条）

**现状**：自动备份不接收密码，落到 Documents 或 WebDAV 的是明文 JSON。这与「root 下也翻不出明文」的验收有张力——canary 扫描里已把「明文导出」单独列出。

**方案 A：保持现状 + 更醒目的提示。**
- 改动面：设置页文案与一处提醒；无数据格式变化。
- 风险：用户以为「加密应用」的备份也是加密的。
- 测试计划：文案断言 + 一次 canary 扫描确认行为未变。

**方案 B：用 Keystore 包裹备份密码，自动备份也加密。**
- 改动面：备份配置存储（新增一个 Keystore 包裹的口令）、自动备份调用点、导入路径、以及「忘记密码」的出路。
- 风险：**与「丢不了」直接冲突**——密码一旦只能由本机 Keystore 解出，设备损坏或恢复出厂后备份就打不开，等于把备份变成了同机可用。要缓解，必须在设置时强制「再输入一次并试解密」。
- 测试计划：加密自动备份往返、密码错误被拒、Keystore 失效后的行为、迁移已有明文备份的提示。

**需要你决定**：A 还是 B。B 要接受「备份与设备绑定」这个新约束。

### 6.3 密钥失效后的出路（对应方案第 14 条）

**现状**：Keystore 条目丢失时库打不开，只能手动清数据后重装再导入。README 规则 5 明确「不新建密钥、不删除、不重建原文件」。

**方案**：应用内提供「把旧库改名保留 + 新建空库」，要求用户输入确认文字（例如输入「新建」）。
- 改动面：`KeyUnavailable` 错误页加一个入口；`EncryptedDatabaseProvider` 增加一条明确的「归档旧文件」路径；规则 5 需要修订。
- 风险：这是「自动重建」的变体，一旦做得太顺手，就等于把「密钥丢失」从硬故障降级成一次点击。旧库改名保留是为了可回滚，但用户也可能在没做备份的情况下把数据留在旧文件里再也想不起来。
- 测试计划：归档后新库可写、旧文件仍在且仍是密文、再次启动不重复归档、`KeyUnavailable` 之外的分支不受影响。

**需要你决定**：是否修订 README 规则 5。修订前不改代码。

### 6.4 备份新鲜度提醒（对应方案第 15 条）

**方案**（纯 UI，不动数据层）：
- 触发条件：`status.localConfigured || status.webDavConfigured`，且存在至少一条笔记，且「最近成功时间」早于 N 天（建议 N=7），且当前不在备份中。
- 呈现：列表顶部一条安静的提示条（serif 15sp、secondary 色、1dp 上边线），一行文案「上次成功备份是 8 天前 · 现在备份」，点整条进设置页。
- 与自动备份状态的关系：直接用 `BackupStatusStore` 现成的 `localLastSuccessAt` / `remoteLastSuccessAt` 取较大者；不新增状态。
- 风险：误报（比如用户只用 WebDAV 且刚好失败）——所以取两个目的地的较大值，且失败不触发、只有「太久没成功」才触发。
- 测试计划：时间源注入，7 天整与 6 天 23 小时分别断言；无笔记不显示；备份进行中不显示。

**需要你决定**：N 取几天，以及是否要点进设置页（还是只提示）。

## 9. 请在手机上验证的事

1. **中文输入法组合态**：按 `scripts/ime-composing-manual.md` 走一遍，重点看「拼音不选字停 1.5 秒再上屏」是否还会重复或丢字。修法是保留 composition，但真机 IME 的行为只能你来看。

6. **预测性返回手势**：从编辑页半途松手（取消返回），确认文本没丢、没多出一条空笔记。
