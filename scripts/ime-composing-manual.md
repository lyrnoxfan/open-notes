# 中文输入法组合态：实机手测脚本

自动化能覆盖的部分已经写在测试里（见 §三 的结论），**组合态本身只能在真机上用真输入法看**：
Compose 只把 `InputConnection` 交给系统输入法，测试进程拿不到，所以没有可靠的注入点。

以下步骤在手机上按顺序做一遍，每步后面是要观察的点。装 debug 包即可。

## 准备

1. 手机装两个输入法：**Gboard** 和**系统自带输入法**（ColorOS 上是百度定制版）。
2. 设置 → 系统 → 语言与输入法，把两者都启用，先默认 Gboard。
3. 打开应用 → 新建笔记 → 点正文区，让键盘弹出。
4. 想留证据时另外接一台设备录屏；本机 `adb shell screenrecord` 录不到画面——
   `FLAG_SECURE` 一直开着，这是设计如此，不要为录屏关掉它。

## 用例 1：拼音未上屏时停顿（最关键）

1. 在正文里输入 `nihao shijie`（**不选字**，让候选栏留在屏幕上）。
2. **停 1.5 秒**（超过 1 秒的自动保存窗口）。
3. 再选字上屏，选「你好世界」。

观察：

- ✅ 正确：上屏后正文是 `你好世界`。
- ❌ 典型故障：变成 `nihao shijie你好世界`、`你好世界` 重复两次、或候选栏突然消失后
  只上屏了最后一个字。看到任何一种，记下发生位置（第几个字之后）。

## 用例 2：长文中间插入

1. 正文先输入 5–6 行中文（每行十几个字），等状态显示「已保存」。
2. 把光标点到**第二行中间**，输入 `ceshi` 再选「测试」。

观察：插入点是否准确、前后文是否被吃掉、有没有把整段替换掉。

## 用例 3：连续快速输入

1. 不清空，连续快速打三句拼音并逐句上屏（间隔 < 1 秒）。

观察：是否出现字序错乱、丢字。这一条同时压自动保存的竞态。

## 用例 4：切换输入法

1. 输入 `nihao`（不选字）→ 直接切到另一个输入法 → 切回来 → 继续选字。

观察：切换后候选栏是否还在、已输入的拼音是否保留。

## 用例 5：英文与 emoji 混排

1. 输入 `hello 世界 🌙` 再补一句中文，退出编辑页再进来。

观察：逐字节是否一致（emoji 不变成 `?`，不出现半个代理对）。

## 记录什么

每条用例记三行：

```
用例：1     输入法：Gboard 12.x    结果：❌ 重复上屏「你好世界你好世界」
复现率：5/5（每次停顿 1.5s 都出现）  位置：正文第 3 行
备注：不停顿时不出现；停顿 < 0.8s 也不出现
```

复现率是这次报告里最有用的数字：**停顿超过自动保存窗口（1 秒）才触发**，说明它和状态回写
有关，而不是键盘本身的问题。如果只在 Gboard 上出现、系统输入法正常，也请记下来。

## 已知的代码级原因（供对照，不用在手机上验证）

`NoteEditorScreen.EditorBody` 每帧都重建输入框的值：

```kotlin
value = TextFieldValue(text = content, selection = selection)
```

`TextFieldValue` 的这个构造函数没有 `composition` 参数，所以组合区（还没上屏的拼音）在每次
重建时被丢掉。而 `content` 每个按键都会经 ViewModel 回写一次，于是**只要状态回写发生在组合
过程中，组合区就会被清掉**。修复方向见 `docs/test-report.md` §三：把 `TextFieldValue` 留在
编辑器本地，只在 `text` 真的变化且没有组合态时同步，并把 `composition` 一起保留。
